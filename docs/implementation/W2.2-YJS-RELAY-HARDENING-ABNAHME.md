# W2.2 – Yjs-Relay-Härtung – Abnahme

**Stand:** 2026-07-25  
**Geltungsbereich:** Quiz-Sammlungs-Sync auf Port 3002 / `/yjs-ws`

## Umgesetzter Scope

- Der Backend-Prozess startet keinen ungefilterten
  `@y/websocket-server`-Entry mehr. Ein eigener in-process Relay kontrolliert
  jeden HTTP-Upgrade und verwendet die Paket-Utilities nur für das kompatible
  Yjs-Protokoll.
- Zulässig ist ausschließlich
  `/quiz-library-room-<UUID>` ohne Query oder zusätzliches Pfadsegment. Die UUID
  wird intern kleingeschrieben; andere Dokumentnamen werden vor dem Upgrade
  verworfen.
- `ws.maxPayload` begrenzt jede Nachricht fest auf **2 MiB**.
- Standardgrenzen je Backend-Prozess:
  - 1.000 aktive Yjs-Verbindungen global,
  - 200 aktive Verbindungen pro Raum,
  - 3.000 Upgrade-Versuche pro Minute global,
  - 600 Upgrade-Versuche pro Minute und Raum,
  - 600 Nachrichten pro Verbindung und zehn Sekunden.
- Env kann diese Grenzen bis zu dokumentierten statischen Code-Maxima
  konfigurieren. Es gibt bewusst kein enges IP-Limit.
- Nach Trennung des letzten Clients wird das flüchtige In-Memory-Yjs-Dokument
  zerstört. Der Relay persistiert weiterhin keine Quiz-Sammlung.
- `HealthSecurityStatsDTOSchema` definiert vor der Backend-Ausgabe aktive
  Yjs-Verbindungen/Räume, konfigurierte Verbindungscaps sowie Upgrade-,
  Payload- und Nachrichtenraten-Ablehnungen.

## Automatisierte Abnahme

`apps/backend/src/lib/yjsRelay.test.ts` prüft mit echten WebSocket-Upgrades:

1. gültiger UUID-Raum verbindet, beliebige Räume und Query-Varianten werden mit
   HTTP 400 abgewiesen,
2. globale und raumbezogene Verbindungscaps antworten mit HTTP 503,
3. das globale Upgrade-Budget antwortet mit HTTP 429 und ist nicht IP-basiert,
4. eine überschrittene Nachrichtenrate schließt mit WebSocket-Code 1013,
5. ein Payload über 2 MiB schließt mit WebSocket-Code 1009,
6. Env-Werte können die statischen Maxima nicht überschreiten.

Die Telemetrie- und Health-Tests prüfen Zähler, Schema und die ausschließlich
diagnose-authentifizierte Ausgabe. Der bestehende
`scripts/load/yjs-sync-load.mjs` bleibt das fachliche Gate für mehrere Clients,
konkurrierende Updates, Offline-Änderungen und Reconnect-Konvergenz.

## Local-First-/Produktionsabnahme

Vor Merge sind mindestens auszuführen:

```bash
npm run build
npm run lint
npm test

# Backend mit PostgreSQL/Redis und produktionsähnlichen Env-Werten:
CLIENTS=30 npm run load:yjs:sync
```

Die Lastläufe müssen initiale Konvergenz, Reconnect aller vorgesehenen Clients,
Übernahme der Offline-Updates, gemeinsame State-Vektoren und null
Providerfehler melden. Ein lokaler Browser-Smoke
`npm run smoke:quiz-sync -w @arsnova/frontend` prüft zusätzlich Linkimport und
Live-Übernahme zwischen Browserkontexten.

### Ergebnis vom 2026-07-25

Die Abnahme lief gegen das gebaute Produktionsimage als Non-Root-Container mit
read-only Rootfs, leerem Capability-Set, `no-new-privileges` und begrenztem
`/tmp`:

- 30 Clients, davon 6 Offline-Reconnects: 0 Fehler,
- Initial Connect/Sync p95: 77 ms,
- Reconnect p95: 258 ms, Resync p95: 261 ms,
- initiale und erneute Konvergenz: jeweils 3 ms,
- Browser-Smoke: zweites Gerät importiert denselben Raum, lokaler Altstand
  fließt nicht zurück, spätere Umbenennung kommt live an,
- Container-/Chromium-Runtime-Smoke: bestanden.

## Bewusste Abgrenzung und Risiken

- Die Raum-UUID bleibt in diesem Slice ein Bearer-Secret mit vollem
  Lese-/Schreibzugriff. Signierte langlebige Share-Tokens und manuelle Rotation
  sind in
  [ADR-0033](../architecture/decisions/0033-harden-yjs-relay-and-plan-rotatable-share-tokens.md)
  konzipiert, aber weder im Relay noch im Frontend implementiert.
- Ältere, nicht UUID-förmige Sync-IDs, die das Frontend historisch akzeptieren
  konnte, erreichen den Relay nicht mehr. Regulär erzeugte Raum-IDs verwenden
  `crypto.randomUUID()`.
- Limits und Dokumentzustand gelten pro Backend-Prozess. Horizontale Skalierung
  braucht gemeinsame Admission-Control und eine Yjs-Verteilung bzw. Sticky
  Sessions.
- Eine explorative 100-Client-Raumlast verfehlt mit dem bestehenden Lastskript
  das Reconnect-Gate: 12 von 20 reconnectenden Clients erreichen den
  Sync-Status erst nach dem 15-Sekunden-Phasentimeout. Derselbe Verlauf tritt
  mit dem unveränderten Upstream-Entry auf; die W2.2-Telemetrie zeigt dabei
  keine Cap-/Rate-/Payload-Ablehnung. Das ist keine durch diesen Slice
  eingeführte Regression, bleibt aber vor einer Erhöhung des regulären
  30-Client-Gates separat zu analysieren.
- Ein einzelner über dem Nachrichtenbudget liegender Frame kann noch vom
  Protokollhandler gelesen werden, bevor der Socket geschlossen wird; das feste
  2-MiB-Cap begrenzt die Arbeit. Die Verbindung verarbeitet danach keine
  weiteren Frames.
- Awareness- und Yjs-Inhalte werden weiterhin nur protokollseitig, nicht
  fachlich gegen Quiz-Schemas validiert. Ein Besitzer des Links kann den
  gemeinsamen CRDT-Zustand manipulieren.

## Rollback

Bei einer Sync-Regression den W2.2-Commit zurückrollen und das vorherige Image
deployen. Es gibt keine Datenmigration und keine persistente Relay-Datenbank.
Vorher Backend-/Proxy-Logs, `health.securityStats` und den fehlgeschlagenen
Yjs-Loadreport sichern. Ein Rollback stellt den ungefilterten Paket-Entry wieder
her und entfernt damit die neuen Schutzgrenzen; er ist nur eine kurzfristige
Verfügbarkeitsmaßnahme.
