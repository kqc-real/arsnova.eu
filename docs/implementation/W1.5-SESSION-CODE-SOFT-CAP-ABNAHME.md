# W1.5-Abnahme: NAT-tauglicher Session-Code-Schutz

**Stand:** 2026-07-24
**Owner:** Backend / Security
**Ticket:** Branch `security/w1.5-session-code-soft-cap`
**Abhängigkeit:** Redis für den ausschließlich ungültigen Join-Pfad

## Schutzmodell

- `JoinSessionInputSchema` verlangt eine browserweite zufällige
  `anonymousClientId` als UUID. Sie ist kein Proof, enthält keine PII und wird
  im Backend nur gehasht für Redis-Keys verwendet.
- `session.join` lädt zuerst die Session. Gültige, nicht beendete Sessions
  berühren kein Fehlbudget. Rejoins umgehen zusätzlich die bestehende
  Join-Wellen-Glättung.
- Nur nicht existente Codes buchen Client-, Code- und Globalzähler gemeinsam in
  einem Lua-Aufruf. Der Client-Cap kann ausschließlich ungültige Requests mit
  429 ablehnen.
- Code- und Global-Soft-Caps erzeugen ab 80 % einen progressiven Delay zwischen
  100 und 1.500 ms plus aggregierte Telemetrie, aber keinen Hard-Lock.
- Ab vollem Globalbudget legt Lua keine neuen Client-/Code-Keys an. Die
  Kardinalität je Fenster ist dadurch durch das globale 5.000er-Maximum
  begrenzt. Alle Budget-Keys haben 300 Sekunden TTL.
- Bei Redis-Ausfall bleiben gültige Joins unbeeinträchtigt. Nicht existente
  Codes schlagen konsistent fail-closed fehl.

## Statische Maxima

- Client: 20 ungültige Codes je 300 Sekunden
- Code-Soft-Cap: 600 je 300 Sekunden
- Global-Soft-Cap: 5.000 je 300 Sekunden
- Delay: 100–1.500 ms

Alle Werte können über die dokumentierten Env-Variablen nur abgesenkt werden.

## Automatisierte Akzeptanz

- Shared Contract: erforderliche gültige UUID; fehlende/manipulierte IDs werden
  abgelehnt.
- Frontend: UUID wird browserweit in `localStorage` stabilisiert und bei jedem
  Join-/Auto-Rejoin gesendet.
- Backend: gültige Joins und Rejoins umgehen Fehlbudgets; 500 gültige Inputs
  werden unabhängig von gemeinsamer IP zugelassen.
- Zwei anonyme Clients teilen trotz gleicher IP keinen Client-Key.
- Client-Cap ergibt 429; Code-/Globaldruck ergibt bounded Delay und Telemetrie.
- Parallele Fehlversuche laufen jeweils in genau einem atomaren Lua-Aufruf.
- Ein opt-in Redis-Regressionstest führt das Lua-Skript im CI-Classroom-Job
  tatsächlich aus und prüft Client-Cap, Code-Delay, TTL und die
  Kardinalitätsgrenze nach globaler Sättigung.
- Redis-Keys enthalten weder IP noch rohe Client-ID; nach globaler Erschöpfung
  entstehen keine neuen angreiferkontrollierten Keys.
- `health.securityStats` liefert Fehler, Delays und globale Auslastung ohne
  IDs, Codes oder IPs.
