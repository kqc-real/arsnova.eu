# W1.6b-Abnahme: Progressive Admin-Login-Härtung

**Stand:** 2026-07-24  
**Owner:** Backend / Security  
**Ticket:** PR-Slice W1.6b  
**Abhängigkeiten:** Redis, W1.6a-Telemetrie  
**Rollback:** Code-Revert oder kontrollierte Anpassung der Rate-Limit-Env

## Schutzmodell

- Nur ungültige `admin.login`-Versuche werden in einem globalen Redis-Fenster
  gezählt. Das schützt das einzelne globale Shared Secret auch gegen
  IP-verteilte Angriffe.
- Die Verzögerung steigt exponentiell von standardmäßig 100 ms auf höchstens
  2000 ms. Das Fehlbudget erlaubt standardmäßig 60 Versuche pro 60 Sekunden.
- Maximal 25 verzögerte Requests warten gleichzeitig pro Backend-Prozess.
  Weitere ungültige Versuche erhalten sofort `TOO_MANY_REQUESTS`.
- Nach ausgeschöpftem Globalbudget liefert der Server eine positive
  `retryAfterSeconds`-Angabe über den bestehenden tRPC-Error-Transport.
- Das Admin-Frontend lokalisiert die Drosselungsmeldung und zeigt die konkrete
  Wartezeit in allen fünf gepflegten Sprachen.
- Gültige Zugangsdaten umgehen das Fehlbudget und erzeugen weiterhin nur ein
  kurzlebiges, Redis-gestütztes Admin-Session-Token.
- Es gibt bewusst weder einen Admin-IP-Key noch einen IP-Lockout. Damit kann
  ein Angreifer keine gemeinsam genutzte Hochschul-/Betreiber-IP sperren.
- 429-Ablehnungen sind in `health.securityStats` unter der Kategorie
  `adminLogin` und in den gesampelten `rate_limit_429`-Logs sichtbar.

## Abnahmekriterien

- [x] Ungültige Admin-Logins werden global und atomar gezählt.
- [x] Wiederholte Fehlversuche erhalten einen progressiv steigenden Delay.
- [x] Globalbudget und wartende Requests sind hart begrenzt.
- [x] Gültige Admin-Zugangsdaten bleiben unter Fehlversuchslast nutzbar.
- [x] Es entsteht kein IP-basierter Lockout.
- [x] 429 enthalten eine positive Wartezeit und sind als `adminLogin` messbar.
- [x] Die Admin-UI zeigt lokalisierte Rate-Limit-Meldung und Wartezeit.
- [x] Env-Beispiele, Admin-Flow und Monitoring-Runbook sind aktualisiert.
