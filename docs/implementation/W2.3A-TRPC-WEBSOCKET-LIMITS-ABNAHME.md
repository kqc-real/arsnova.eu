# W2.3a – tRPC-WebSocket-Limits – Abnahme

**Stand:** 2026-07-25  
**Geltungsbereich:** tRPC-Subscriptions auf Port 3001  
**Abhängigkeit:** gestapelt auf W2.2 / PR #137

## Umgesetzter Scope

- Ein eigener `TrpcWebSocketServer` prüft HTTP-Upgrades vor dem
  `@trpc/server`-Handler und Nachrichten vor dem tRPC-Parser/Resolver.
- Standardgrenzen je Backend-Prozess:
  - 1.000 gleichzeitig aktive Verbindungen (Code-Maximum 5.000),
  - 3.000 Upgrade-Versuche pro Minute (Code-Maximum 30.000),
  - 120 Nachrichten je Verbindung und zehn Sekunden (Code-Maximum 1.200),
  - 30.000 Nachrichten global und zehn Sekunden (Code-Maximum 300.000).
- Es gibt bewusst keine IP-Buckets. Eine Schule oder Hochschule hinter Shared
  NAT wird als Gesamtheit weder gesperrt noch enger gedrosselt.
- Das bestehende, codefeste Einzelpayload-Cap bleibt unverändert bei **2 MiB**.
  Überschreitungen schließt `ws` weiterhin mit Code `1009`.
- Erschöpfte Upgrade-Budgets antworten vor dem WebSocket-Handshake mit HTTP
  `429`, das Verbindungscap mit `503`. Ein Nachrichtenraten-Verstoß terminiert
  den Socket; der überschreitende Frame erreicht keinen tRPC-Resolver.
- `HealthSecurityStatsDTOSchema` definiert schema-first das konfigurierte
  Verbindungscap sowie rollierende Upgrade-, Payload- und
  Nachrichtenraten-Ablehnungen. Die Query bleibt diagnose-authentifiziert.

## Herleitung gegen 500er-SLO

Die Defaults sind keine aus IP-Adressen abgeleiteten Sicherheitsnachweise,
sondern prozessweite Ressourcengrenzen mit Reserve:

- 1.000 Verbindungen tragen zwei vollständige 500er-Kohorten.
- 3.000 Upgrades/Minute tragen sechs vollständige 500er-Reconnect-Wellen. Eine
  einzelne Welle bleibt damit deutlich unter dem Cap und kann weiterhin das
  Reconnect-SLO p95 ≤ 3 s / p99 ≤ 5 s erreichen.
- 30.000 Nachrichten/10 s entsprechen bei 500 gleichzeitig verbundenen
  Clients 60 eingehenden Nachrichten pro Client und Fenster. Das liegt weit
  oberhalb des regulären Subscribe-/Interaktionsprofils, begrenzt aber
  unbeschränktes Parser-Fan-in.
- 120 Nachrichten/10 s je Verbindung lassen kurzfristige Client-Bursts zu,
  ohne einem einzelnen Socket das gesamte Globalbudget zu überlassen.

Diese Werte dürfen per Env nur bis zu statischen Code-Maxima erhöht werden.
Produktionswerte werden nach realen Telemetriedaten überprüft, nicht spontan
während einer Veranstaltung verschärft.

## Automatisierte Abnahme

`apps/backend/src/lib/trpcWebSocketServer.test.ts` prüft mit echten
WebSocket-Upgrades:

- HTTP `503` oberhalb des aktiven Verbindungscaps,
- HTTP `429` oberhalb des Upgrade-Minutenbudgets,
- Abbruch vor dem tRPC-Resolver bei Verbindungs- und Globalbudget,
- unverändertes 2-MiB-Cap mit Close-Code `1009`,
- Telemetrie für alle Ablehnungsarten,
- eine vollständige 500-Client-Verbindungs- und Reconnect-Welle mit den
  Standardlimits.

`apps/backend/src/lib/websocketTelemetry.test.ts` prüft Zähler und Cap-Snapshot;
`apps/backend/src/__tests__/health.test.ts` prüft die
diagnose-authentifizierte DTO-Ausgabe. Die bestehenden Last-Smokes bleiben:

```bash
npm run load:smoke:ws-reconnect-wave-classroom-30
PARTICIPANTS=500 npm run load:artillery:reconnect:500
```

## Bewusste Abgrenzung

- Kein Participant-/Session-Binding in diesem Slice.
- Kein clientseitiger jittered Reconnect in diesem Slice.
- Keine IP-basierte Teilnehmerdrosselung.
- Keine Änderung an A11y-, Frontend- oder Playwright-Baselines.

Diese Punkte gehören zu W2.3b beziehungsweise separaten fachlichen Arbeiten.
