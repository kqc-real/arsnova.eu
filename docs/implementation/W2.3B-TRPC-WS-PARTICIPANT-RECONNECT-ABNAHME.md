# W2.3b — tRPC-WebSocket Participant-Binding und Reconnect-Abnahme

**Stand:** 2026-07-25  
**Owner:** Backend/Frontend Platform  
**Ticket:** W2.3b aus `SECURITY-HARDENING-PLAN.md`  
**Abhängigkeit:** W2.3a (globales Upgrade-, Verbindungs-, Nachrichten- und festes 2-MiB-Payload-Cap)  
**Rollback:** Commit/Deployment dieses Slices zurückrollen oder die neuen
Session-/Participant-Env-Werte bis zu ihren statischen Maxima anheben. Die
globalen W2.3a-Caps bleiben in beiden Fällen aktiv.

## Scope und Sicherheitsmodell

Der globale lazy tRPC-WebSocket-Client sendet auf Session-Routen im ersten
`connectionParams`-Frame:

- den auf sechs alphanumerische Zeichen normalisierten Session-Code,
- optional die lokal unter `arsnova-participant-${code}` gespeicherte UUID,
- unverändert benötigte Host- beziehungsweise Feedback-Host-Tokens.

Code und UUID enthalten keine PII und sind ausschließlich Throttle-Signale.
Sie sind weder ein Authentifizierungs- noch ein Besitznachweis. Host-Rechte
werden weiterhin ausschließlich über die bestehenden Token-Prüfungen erteilt.
Es gibt kein IP-Limit; zwei Clients derselben Campus-NAT verwenden unabhängige
Participant-Buckets.
Das Session-Cap hält für eine 500er-Veranstaltung eine vollständige zweite
Kohorte und 100 zusätzliche Steuer-Sockets frei, damit noch nicht erkannte
stale Sockets eine Reconnect-Welle und Host-/Presenter-Verbindungen nicht
verdrängen. Host-/Present-Routen senden weiterhin den Session-Code, aber keine
eventuell lokal gespeicherte Participant-ID.
Ein zentraler Fingerprint aus Session-Code und optionaler Participant-UUID
erkennt SPA-Navigation sowie eine nach dem Join gespeicherte UUID. Bei einer
Änderung schließt der globale Client nur den bisherigen physischen Transport.
Der tRPC-Reconnect hält aktive Subscription-Requests dabei pending und sendet
sie nach Aufbau des Sockets mit aktuellen `connectionParams` erneut. Neue
Subscription-Starts warten auf diesen Wechsel; ohne aktive Subscription öffnet
der nächste Start den Socket weiter lazy. Unveränderte Fingerprints,
Host-/Feedback-Tokens und das Lazy-Close-Verhalten bleiben unberührt.

Der Server erkennt nur textuelle `connectionParams`-Frames bis 16 KiB für
diese Vorprüfung. Das eigentliche WebSocket-Payload-Cap bleibt unverändert bei
2 MiB. Ungültige, fehlende oder alte Params erzeugen kein Binding und bleiben
unter den globalen Caps kompatibel.

## Limits und Lifecycle

| Grenze                         | Default | statisches Maximum |
| ------------------------------ | ------: | -----------------: |
| global aktive tRPC-WebSockets  |   1.200 |              5.000 |
| je signalisiertem Session-Code |   1.100 |              5.000 |
| je Session-/Participant-Tupel  |       2 |                 10 |

Die prozesslokalen Maps wachsen höchstens mit erfolgreich gebundenen aktiven
Sockets. Admission prüft Session- und Participant-Cap vor beiden Inkrementen.
Ein Close gibt das Binding genau einmal frei; Zähler mit Wert null werden
gelöscht. Mehrere Subscriptions desselben physischen Sockets buchen kein
weiteres Binding. Eine Cap-Ablehnung schließt nur den überschreitenden Socket
mit Policy-Code 1008.

`health.securityStats` veröffentlicht nur aggregierte Werte:

- aktive gebundene Verbindungen,
- konfigurierte Session-/Participant-Caps,
- Session- und Participant-Cap-Ablehnungen der letzten Minute.

Codes und UUIDs werden weder im DTO noch in Logs offengelegt.

## Reconnect-Modell und Gate

Produktclient und Last-Runtime verwenden 500 ms, 1 s, 2 s, 4 s bis maximal
10 s exponentielles Backoff plus jeweils 0–349 ms Jitter. Das
Artillery-Szenario wartet auch vor der explizit erzeugten Neuverbindung den
produktnahen ersten Jitter-Schritt und übermittelt das Participant-Binding.

Formales Gate aus dem Härtungsplan:

> Mindestens 95 % von 500 Clients sind innerhalb von 30 Sekunden wieder
> verbunden.

Join-Quote, `RESULTS`-Fan-out, Subscription-Fehler und Recovery werden
zusätzlich berichtet, ohne das formale 30-Sekunden-Gate durch ein
undokumentiertes Max-Latenz-Gate zu ersetzen.

## Automatisierte Abnahme

Die fokussierten Tests decken ab:

1. gültiges Binding und mehrere Subscriptions auf einem Socket,
2. Ablehnung der dritten Verbindung derselben Participant-ID,
3. zwei Participants derselben NAT/IP ohne gegenseitige Blockade,
4. Session-Cap über verschiedene Participant-IDs,
5. exakte Counter-Freigabe nach Close,
6. malformed/ungültige Params fail-safe,
7. Legacy-Clients ohne Params,
8. A→B-SPA-Navigation mit wiederverwendetem Client, Socket-Close und frischem Binding,
9. Binding-Erneuerung nach Speicherung der Participant-ID bei weiterhin aktiver Subscription,
10. Frontend-Params einschließlich Host-/Feedback-Token,
11. exponentielles Backoff und 0–349-ms-Jitter,
12. unverändertes 2-MiB-Payload-Cap und W2.3a-Grenzen.

Auszuführende Gates:

```bash
npm run test -w @arsnova/shared-types
npm run test -w @arsnova/backend -- src/lib/trpcWebSocketServer.test.ts src/lib/websocketTelemetry.test.ts src/__tests__/health.test.ts
npm run test -w @arsnova/frontend -- src/app/core/trpc.client.spec.ts
npm run typecheck
npm run lint
npm test
PARTICIPANTS=500 npm run load:artillery:reconnect:500
```

Der 500er-Lauf ist ein autorisierter manueller/Schedule-Abnahmelauf und darf
nicht ungeplant gegen Produktion ausgeführt werden.

## Ergebnis 2026-07-25

Der isolierte lokale 500er-Lauf gegen den aktuellen Branch bestand:

- 500/500 Joins, 0 Join-Fehler,
- 500/500 Reconnects innerhalb 30 Sekunden,
- Reconnect maximal 863 ms, Mittelwert 678 ms,
- gemessener Jitter 500–849 ms (p95 837,3 ms),
- 500/500 Clients empfingen `RESULTS` nach dem Reconnect,
- 0 WebSocket-, Reconnect-, Subscription- oder Assert-Fehler,
- Artillery Exit-Code 0.

Zusätzlich bestanden vollständige Monorepo-Tests (34 Shared-, 67
Export-, 624 Backend- und 1.004 Frontend-Tests; dokumentierte Skips
unverändert), Typecheck, Lint und `build:prod`.

## Out of scope

- Participant-ID als Authentifizierung oder serverseitige Session-Mitgliedschaft,
- enge IP-/NAT-Limits,
- Änderung des 2-MiB-Payload-Caps oder der W2.3a-Budgets,
- Redis-/clusterweite Participant-Zähler,
- Yjs-Relay, CSP, A11y oder andere Security-Slices.
